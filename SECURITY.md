# Security

## Reporting a vulnerability

Use GitHub's private vulnerability reporting for this repository. Do not open a public issue for a vulnerability. This is a personal open-source reference project maintained on a best-effort basis: no service level and no bounty. It has not been used in production, has not had an independent security review, and has never been run against the real Stripe API.

## What this is

The payments backend of a two-sided marketplace on Stripe Connect, as a reference core: a seller onboarding state machine, checkout with destination charges, an append-only double-entry ledger, idempotent signed webhooks that survive duplicates and reordering, reconciliation against Stripe, and row level security between sellers in PostgreSQL. Stripe is reached through a port (`StripeGateway`); tests and the demo use an in-process fake. The risks it is designed around, and what answers each:

1. money booked twice or lost when events repeat, race or arrive out of order, 2. a seller seeing or changing another seller's money, 3. the books being rewritten or not balancing, 4. the platform's commission or an amount being manipulated, 5. a forged request pretending to be Stripe.

## Threat model

Every claim names a test that fails if the claim stops being true. Paths are relative to `test/`.

| Threat | What the code does | Test |
| --- | --- | --- |
| A webhook is forged, altered, stale or unsigned | HMAC-SHA256 over the raw bytes with a timestamp, constant-time comparison against every `v1` value and every secret, schemes other than `v1` ignored, tolerance 5 minutes (configurable), checked BEFORE the body is parsed; answer 401 without a reason | `infrastructure/http.test.ts` ("the webhook signature", "the webhook server"), `integration/server.pg.test.ts`; demo section 3 |
| Unsigned traffic floods the endpoint or the log | Failed signatures are counted per address only to answer 429 and to stop logging; a valid signature always gets through; `X-Forwarded-For` is ignored unless a trusted proxy depth is configured; the body is size-limited while it is read | `infrastructure/http.test.ts` ("what unauthenticated traffic can and cannot do") |
| The same event is delivered twice, or at the same moment | The event id is the idempotency key; the event is recorded and applied in one transaction behind a lock per charge, payout or account | `contract/webhooks.scenarios.ts` ("applies a duplicate delivery once", "eight times at the same moment"), `integration/server.pg.test.ts` (20 identical requests at once) |
| Events arrive out of order | An event that needs a charge waits for it and is applied in the transaction that records the charge; refund, dispute and payout states only move up in rank; `account.updated` reads the account from Stripe | `contract/webhooks.scenarios.ts` ("holds a refund, a transfer and a dispute", the payout and dispute order tests), `contract/convergence.scenarios.ts` (shuffled, duplicated and concurrent deliveries end in the same books, on both stores) |
| A refund and its charge race and the refund is stranded | Both take the lock of the charge first; a control without the lock shows the refund stranded, and `retryDeferred` is the way out | `integration/adapter.pg.test.ts` ("a refund and its charge arriving at the same moment") |
| One business fact is booked twice | Entries are keyed by the fact (`sale:ch_...`, `refund:re_...`); the key is unique in the database | `integration/schema.test.ts` ("refuses the same posting key twice"), `integration/adapter.pg.test.ts` (four connections post one fact) |
| An event is half applied | The event row and everything it changes are one transaction; a failure rolls all of it back and the answer is 5xx so Stripe sends it again | `contract/webhooks.scenarios.ts` ("leaves nothing behind when the application fails half way", "does not record an `account.updated` event when Stripe cannot be reached"), `integration/server.pg.test.ts` (500 and then applied) |
| The caller sets or tampers with the fee | The fee is computed by the platform; the checkout request has no fee field; the order stores the fee and a charge that differs is booked as Stripe took it and flagged | `contract/checkout.scenarios.ts` ("has no way for the caller to set the fee"), `contract/webhooks.scenarios.ts` ("books what Stripe took even when it differs from the order") |
| Fee rounding creates or loses a cent, or a float reaches Stripe | Integers of the minor unit, half-up rounding in BigInt, a fee that would leave the seller nothing is refused and never clipped; refund parts add up exactly to the fee and the net in any order | `domain/money.test.ts` (2,000 random policies and amounts, 500 random refund series), `contract/checkout.scenarios.ts`, `contract/money.scenarios.ts` ("splits every refund between seller and platform ...") |
| A refund is bigger than the charge, or in another currency | Rejected and recorded with the reason; nothing is booked | `contract/webhooks.scenarios.ts` ("refuses a refund or a dispute that is more than the charge"), `contract/money.scenarios.ts` ("never refunds more than what is left") |
| A refund after the payout | The ledger records the debt (negative seller balance), stays balanced, and reconciliation names it as a warning | `contract/money.scenarios.ts` ("a refund after the payout") |
| A dispute is lost on money that was already refunded, and the amount stays held for good | A lost dispute charges seller and fee only for what the sale has left, in proportion, and the platform bears the rest, so `disputed_funds` is released and the books balance; refunds that add up to more than the charge are still rejected; either order of the two events ends in the same books | `contract/money.scenarios.ts` ("a dispute that is lost after the same money was refunded"), `contract/convergence.scenarios.ts` |
| Money goes to an account that is not the order's seller | The charge is rejected, nothing is booked, the event is kept for a person, and reconciliation reports the charge Stripe took | `contract/webhooks.scenarios.ts` ("rejects a charge that pays another account"), `contract/reconciliation.scenarios.ts` |
| A seller reads another seller's ledger or orders | Three locks: the use case refuses, the query filters on the seller id, and the database role of a seller only sees rows that carry their id; the platform's side of an entry is hidden | `contract/isolation.scenarios.ts`, `integration/rls.test.ts` ("a seller") |
| A seller or an operator writes | A seller and an operator have no write privilege on any table; the system role has INSERT and UPDATE of named columns only and no DELETE | `contract/isolation.scenarios.ts` ("cannot write anything"), `integration/rls.test.ts` ("a seller", "an operator", "the system") |
| A request without an identity, or with a malformed one | The claim is NULL and matches nothing; a claim that is not a UUID fails the statement; the role and the claim never come from caller input | `integration/rls.test.ts` ("without an identity"), `integration/adapter.pg.test.ts` ("never builds the role or the claim from what the caller passes") |
| The ledger is rewritten | No UPDATE, DELETE or TRUNCATE on the ledger for anyone, the owner and a superuser included (triggers); no privilege either | `integration/schema.test.ts` ("the ledger is append-only"), `integration/rls.test.ts` ("can append to the ledger and never change or remove a line of it"); demo section 7 |
| An entry does not balance, or a line is added to an old entry | Each entry declares its line count and total; a deferred trigger checks debits, credits, count and total at COMMIT | `integration/schema.test.ts` (unbalanced, no lines, a line smuggled in later, a wrong total) |
| A rejected seller is brought back to life | `rejected` has no way out in the state machine; a refused move is recorded and flagged; the database refuses it too | `domain/seller.test.ts`, `contract/onboarding.scenarios.ts` ("keeps a rejected seller rejected"), `integration/schema.test.ts` ("the state of a seller") |
| A checkout for a seller who cannot take payments | Only `enabled` is sold for; every other state is refused before anything is written | `contract/checkout.scenarios.ts` ("sells only for a seller whose account is enabled") |
| A retried purchase is booked twice | One order per idempotency key and seller, enforced by a unique index; the Stripe call uses a key made from the order id; another request under the same key is a conflict | `contract/checkout.scenarios.ts` (same key, ten at once, Stripe failure then retry) |
| A request turns a checkout or an onboarding link into an open redirect | The origin is configuration; a request names a path on it, and anything that could change the origin is refused | `domain/url-ids.test.ts`, `contract/checkout.scenarios.ts`, `contract/onboarding.scenarios.ts` |
| SQL injection | Every statement uses bind parameters; the only interpolations are a role name from a fixed map and a list of numbered placeholders, and a test lists them | `architecture/layers.test.ts` ("the SQL of the adapter") |
| Errors leak internals | The server answers `internal_error` and logs the error class only; gateway errors carry fixed sentences and never the response body, the URL or the key | `infrastructure/http.test.ts`, `infrastructure/http-gateway.test.ts` |
| Secrets or card data reach a log | The logger replaces the value of any field whose name says it is sensitive; ids and amounts are all that use cases log | `infrastructure/system.test.ts` |
| The adapter for the real API follows a redirect, accepts a plain http URL or reads an unbounded body | https only (plain http for loopback), redirects are not followed, responses are size-capped, timeouts, no retries inside the adapter | `infrastructure/http-gateway.test.ts` |
| A connection that dies in the middle of a transaction ends the process | The connection is thrown away and the error is reported through the pool's handler | `integration/adapter.pg.test.ts` ("keeps working after a connection is killed") |
| The stored events grow into a copy of Stripe's data | The payload is kept only for deferred and rejected events, enforced by a CHECK | `integration/schema.test.ts` ("keeps a payload only for the events that need one"), `contract/webhooks.scenarios.ts` ("drops the stored payload") |
| The demo is pointed at a real server | `createDemoDatabase` refuses any host that is not loopback or a unix socket and uses a role name made for the run | `infrastructure/compose.test.ts`, `integration/demo-db.pg.test.ts` |
| A secret reaches the repository | Secret scanner on commit, push and in CI (tree and history); keys come from the environment | `scripts/secret-scan.sh`; CI job `secret-scan` |
| A dependency is compromised or brand new | One runtime dependency (`pg`), exact pins, every package at least 7 days old at the pin, installs without lifecycle scripts, pinned images and action SHAs | `scripts/check-dep-age.mjs`; CI job `dependency-age` |

## What is not guaranteed

- **It has never talked to Stripe.** The event shapes, the endpoints and the parameters follow Stripe's public API reference; no test used a real Stripe account, the Stripe CLI, a test-mode key or a real webhook delivery. API versions change payloads. Run a complete test-mode flow and `reconcile` before trusting it (docs/adapting.md, the go-live checklist).
- **The adapter for the real API** (`HttpStripeGateway`) has only been run against a fake server on loopback. It creates Express accounts and Checkout Sessions with a destination and an application fee, and nothing else.
- **No audit, no production use.** The CI workflows have not been run on GitHub yet; the commands they call were run locally in containers (README, "What was verified, and how").
- **The money rules are this repository's rules, not Stripe's** (docs/adr/0003). A refund takes the seller's share and the platform's fee share in proportion to the sale; Stripe's own rounding of a reversed transfer can differ by one minor unit, which reconciliation would show. A lost dispute is charged to the seller in the ledger, but at Stripe the platform pays until an operator reverses the transfer: reconciliation reports a balance mismatch until then. Appeals of a lost dispute are not modelled. When a charge in dispute was also refunded, the sale can give back only once: the part of a lost dispute that a refund had already taken from the seller is borne by the platform (`platform_fees` goes below zero, the loss is on the dispute object's `secondary_amount`). If a refund that was applied first fails after such a loss, the ledger keeps the loss on the platform and does not charge the seller after the fact; an operator who then recovers the money from the seller at Stripe sees `balance_mismatch` and `transfer_mismatch` (`contract/money.scenarios.ts`, "keeps the loss on the platform when the refund fails after the loss was applied"). That Stripe lets a disputed charge be refunded, and refuses a refund once the dispute is lost, is how the fake works; it was not checked against the real API.
- **Not modelled:** Stripe's processing fees and dispute fees (the ledger shows the gross sale and the application fee, not the platform's profit), taxes, payment methods that settle later in a different currency than the account's, subscriptions, payout schedules and instant payouts. Nine currencies are known (`CURRENCY_EXPONENT`); anything else is refused, not guessed. The fee policy is one for all of them and is not currency-aware: the fixed fee and the minimum charge are minor units of whichever currency the charge is in (30 is 0.30 USD but 30 yen; `contract/checkout.scenarios.ts`, "applies one fee policy in the minor unit of whichever currency is charged").
- **`livemode` is not checked.** An event is applied whatever its `livemode` flag says; keep test-mode and live-mode endpoints, keys and databases apart.
- **A validly signed event is trusted as Stripe's.** Every secret in `WEBHOOK_SECRETS` verifies every event, so the account endpoint's secret and the Connect endpoint's secret are one trust domain. Data in an event is still checked against the platform's own records (the order, the seller's account, the amounts).
- **Reconciliation sees what Stripe lists.** Disputes are not listed from Stripe, objects older than the window are not compared, and a lost event is found only when `reconcile` runs. Run it on a schedule and alert on its exit code.
- **An account event can overtake its seller's row.** `registerSeller` writes the seller after Stripe has answered; an `account.updated` that arrives in between is recorded as ignored (`unknown_account`) and the seller stays `new` until the next account event. `reconcile` reports the state mismatch and `refreshSeller` repairs it (`contract/onboarding.scenarios.ts`, "loses an `account.updated` event that overtakes the seller's row").
- **A rejected charge leaves its transfer waiting.** A transfer or refund for a charge that was rejected has no sale to belong to; it stays deferred and is reported as stuck after the grace period (default 15 minutes).
- **The database login role.** Anyone who can run arbitrary SQL as it can `SET ROLE` to another application role or set the identity claim. The policies protect against a missing WHERE clause or a wrong id in application code, not against SQL injection in the repositories (none is known; every statement uses bind parameters). The system role reads every table, `stripe_events` included. A superuser or the schema owner can disable a trigger or drop a policy: audit who holds those roles.
- **The operator role has no audit trail.** It reads every seller's rows; reads are not logged by this core.
- **Backups** contain whatever the database contains. The ledger cannot be edited through this core, but a restore from an older backup loses what came after it: run `reconcile` after any restore.
- **Free text.** `buyer_ref` is an opaque reference the caller chooses (letters, digits and `_.:@-`, at most 100 characters); if the caller puts personal data in it, it is stored. Seller display names and order descriptions are stored as given (printable text, length-limited) and are not encrypted at rest by this core.
- **Rate limits** on failed signatures are per process (10,000 addresses, least recently used forgotten). Flooding of unauthenticated traffic must be limited at the reverse proxy.
- **Supabase and its connection pooler** were not used in any test (docs/adapting.md says what to check).
- **Clock.** The signature tolerance and the times of observations use the host clock; entries use Stripe's `created` time of the object, in seconds.
